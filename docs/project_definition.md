# EnterpriseFlow Agent 项目定义

## 1. 项目背景

企业内部通常存在规章制度、项目资料、操作手册、会议纪要和任务数据等多种信息。这些信息往往分散在不同文档、文件夹和业务系统中，员工需要花费大量时间搜索资料，项目负责人也需要在多个系统之间维护项目和任务状态。

现有的大模型聊天应用虽然能够回答自然语言问题，但通常缺少对企业业务数据的访问能力，也无法可靠地执行创建任务、更新状态等实际操作。当大模型直接连接企业业务系统时，还需要解决权限控制、操作确认、结果引用和行为审计等问题。

EnterpriseFlow Agent 计划构建一个面向企业内部知识查询和业务流程操作的智能助手。项目首先实现规范的后端服务和结构化业务数据管理，再逐步加入企业文档检索、Agent 工具调用和自动化评测能力。

本项目不是一个单纯的聊天机器人，也不是一个普通的任务管理系统，而是探索如何将大模型安全地接入真实企业业务能力。

## 2. 目标用户

### 2.1 普通员工

普通员工可以查询自己参与的项目、负责的任务以及企业内部文档。

他们目前面临的主要问题是资料分散、查询入口不统一，难以快速确认自己需要完成的工作，也无法通过自然语言直接查询相关业务信息。

### 2.2 项目负责人

项目负责人可以创建项目、维护项目成员、分配任务和查看项目进度。

他们目前需要手动整理任务信息，项目状态更新不及时，也缺少统一的方式查看成员、任务和文档之间的关系。

### 2.3 系统管理员

系统管理员负责维护用户、角色、企业文档和系统运行状态。

他们需要控制不同用户可以访问和操作的数据范围，并能够追踪重要业务操作的执行人、执行时间和执行结果。

## 3. 核心问题

### 3.1 企业知识和业务数据相互分离

企业文档通常以非结构化形式存在，而项目、用户和任务等数据保存在结构化数据库中。员工提出一个问题时，可能同时需要查询文档内容和业务数据，传统搜索系统难以统一处理这两类信息。

### 3.2 大模型缺少安全执行企业操作的能力

普通聊天机器人只能生成文本，无法可靠地完成创建任务、更新任务状态和查询项目进度等操作。即使接入工具调用，也可能出现参数错误、权限不足、重复执行和不可追踪等问题。

因此，本项目需要在 Agent 和真实业务系统之间增加参数校验、权限检查、操作确认和审计日志机制。

## 4. 项目目标

系统最终需要支持三类能力：

### 4.1 企业知识问答

用户可以使用自然语言查询企业规章制度、项目文档和操作手册。系统返回答案时，需要同时返回引用文档和原文片段。

### 4.2 业务数据查询

用户可以询问：

* 我有哪些未完成任务；
* 某个项目有哪些逾期任务；
* 某位成员当前负责哪些工作；
* 某个项目的任务完成情况如何。

系统需要将自然语言请求转换为受限制的业务查询，而不是允许大模型直接生成任意 SQL。

### 4.3 业务操作执行

用户可以提出创建任务、更新任务状态等请求。

对于会修改数据的操作，系统需要先生成操作预览，在用户确认后执行，并记录完整审计日志。

## 5. 第一阶段功能范围

第一阶段只实现企业业务后端基础，不实现大模型和 Agent。

第一阶段计划实现：

1. 用户信息管理；
2. 项目创建和查询；
3. 项目成员管理；
4. 任务创建、分配、查询和状态更新；
5. 企业文档元数据管理；
6. 操作日志记录；
7. API 参数校验；
8. 自动化测试。

第一阶段暂不实现：

1. 大模型对话；
2. 文档内容解析；
3. 向量检索；
4. Agent 自动调用工具；
5. Web 前端页面；
6. 复杂的组织架构和多级审批流程。

## 6. 核心数据对象

### 6.1 用户 User

用于表示系统使用者。

主要信息包括：

* 用户编号；
* 用户名；
* 邮箱；
* 密码哈希；
* 系统角色；
* 是否启用；
* 创建时间；
* 更新时间。

系统只保存密码哈希，不保存明文密码。

### 6.2 项目 Project

用于表示企业内部项目。

主要信息包括：

* 项目编号；
* 项目名称；
* 项目描述；
* 项目状态；
* 项目负责人；
* 项目创建人；
* 开始日期；
* 计划结束日期；
* 创建时间；
* 更新时间。

### 6.3 项目成员 ProjectMember

用于表示用户和项目之间的成员关系。

主要信息包括：

* 关系编号；
* 项目编号；
* 用户编号；
* 项目内角色；
* 加入时间。

一个用户可以参与多个项目，一个项目也可以包含多个用户，因此需要通过项目成员表表示多对多关系。

### 6.4 任务 Task

用于表示项目中的具体工作。

主要信息包括：

* 任务编号；
* 所属项目；
* 任务标题；
* 任务描述；
* 任务创建人；
* 任务负责人；
* 任务状态；
* 任务优先级；
* 截止时间；
* 完成时间；
* 创建时间；
* 更新时间。

第一阶段一个任务只设置一个主要负责人，后续可以扩展为多个参与者。

### 6.5 文档 Document

用于保存企业文档的基本信息。

主要信息包括：

* 文档编号；
* 所属项目；
* 文档名称；
* 文件类型；
* 文件大小；
* 文件存储位置；
* 上传用户；
* 文档状态；
* 创建时间；
* 更新时间。

第一阶段只管理文档元数据，后续再增加文档解析、文本切分、向量化和检索功能。

### 6.6 操作日志 AuditLog

用于记录系统中的重要操作。

主要信息包括：

* 日志编号；
* 操作用户；
* 操作类型；
* 资源类型；
* 资源编号；
* 操作参数；
* 操作结果；
* 操作时间。

后续 Agent 执行业务操作时，也必须写入操作日志。

## 7. 关键业务约束

系统第一阶段需要遵守以下约束：

1. 用户邮箱不能重复；
2. 项目名称不能为空；
3. 同一个用户不能重复加入同一个项目；
4. 任务必须属于一个项目；
5. 任务负责人应当是该项目的成员；
6. 已停用用户不能创建新的业务数据；
7. 文档必须记录上传用户；
8. 修改任务状态时应记录操作日志；
9. 删除重要业务数据时优先采用逻辑删除，而不是直接物理删除。

## 8. 第一阶段验收标准

第一阶段完成后，系统应该能够：

1. 启动 FastAPI 后端服务；
2. 创建和查询用户；
3. 创建项目并添加项目成员；
4. 为项目成员分配任务；
5. 查询项目任务；
6. 修改任务状态；
7. 保存文档元数据；
8. 记录重要业务操作；
9. 对错误参数返回明确的错误信息；
10. 通过自动化测试验证主要接口；
11. 使用 PostgreSQL 持久化业务数据；
12. 通过 GitHub 提供完整代码和运行说明。
